## 背景：验收发现的问题

v1 的 159 项测试全部通过，但 `s3a_cantilever` 和 `s3a_platform` 只有在任务文件附带 `[proposal]` 时才能求解。这两个 proposal 几乎就是标准答案。用 `run --no-proposal` 运行时，两个任务都在扩展 20 万个状态后返回 `budget`；绕开剪枝直接调用 `_search`，把预算放大到 300 万个状态、约 140 秒，仍然返回 `budget`。

原因是：`bounds.py` / `abstraction.py` 里的下界只用于“已有参考方案上界”时的分支裁剪，而参考方案又依赖 proposal 提供的动作集合。没有 proposal 时，下界完全不起作用。这违背了框架的核心目标：**托住、搭临时支撑台这类辅助步骤必须由系统自己推出，不能由任务文件预先写好。**

## 本轮要完成的事

### 1. 不依赖 proposal 也能求解（最重要）

- 把剩余耗时下界从“只用于剪枝”改为 **A\* 的启发值**：优先队列按（已用时间 + 剩余时间下界，偏离 hint 的次数，序号）排序。没有参考方案时也必须生效。
- 下界必须是**可采纳**的：不能高于真实的剩余最短耗时，以保证结果仍然是当前 cost 模型下的最优解。如果某个下界不能证明可采纳，就不要用于排序和裁剪。
- 可以另外采用不改变最优性的状态空间压缩手段，例如：
  - 同一时刻开始的多个动作按固定顺序生成，避免重复的排列组合；
  - 支配剪枝；
  - 更强的相关动作剪枝，例如禁止把积木放到与目标和后续步骤都无关的位置。

  每采用一种，都要在 README 里说明为什么它不会丢掉最优解，并有对应测试。
- **不得改变 cost 的语义**：动作耗时仍按开始时各臂所在位置的距离计算（`SPEC.md` 第 6.5 节）。
- 保留现有的“有参考方案时用上界裁剪”，但它只能作为附加加速手段。

### 2. 调整示例任务
