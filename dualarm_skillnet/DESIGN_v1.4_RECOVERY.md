# v1.4 设计稿：泛化的在线故障恢复

状态：**框架已于 2026-11-15 逐条确认**（见第 8 节决定）。下一步：v1.3 过夜报告出来后，写 R-M1 的 Codex 交接单。

## 0. 一句话

执行中出了任何故障，系统都走同一条路：**测量 → 换算成规划层的事实 → 更新能力表和排除约束 → 从当前状态重新搜索 → 从当前关节重新编译 → 拼接回执行**。恢复逻辑里不出现任何场景名、积木名或预设分支；"泛化"靠的是故障被翻译成**通用的事实变化**，而不是靠为每种故障写处理代码。

和原项目（Scene1/Scene3）的区别：原来的恢复模型是按场景手写的（`recovery/model.py` 里的 State/Action 和场景文件绑定），现在恢复直接复用 v1.3 的任务文件、技能库、A* 搜索和真实运动后端，所以**换任务不用改恢复代码**。

---

## 1. 要解决的问题边界

| 考虑 | 不考虑（本轮） |
|---|---|
| 执行中由仿真器测到的故障：抓空/滑落、放置偏差、臂或技能持续失效、支撑中断、交接失败、路径被挡 | 力学模型、材料变形 |
| 暂时性与持续性两类故障，先重试再升级 | 传感器本身出错（假阳性） |
| 一只臂出故障时另一只臂尽量不停 | 三臂以上 |
| 掉落的积木落在任意位置（平放、任意偏航） | 积木侧翻、叠在别的积木上（归为"需人工干预"，记录不处理） |
| 恢复后仍满足持物和持续支撑约束 | 执行中更改任务目标 |

## 2. 架构：五个通用部件

```
          ┌──────────────┐  故障事件/周期测量  ┌───────────────┐
 CoppeliaSim│ controller   │ ─────────────────▶ │ ① 监视器      │
 执行中     │ (事件式 TPG) │ ◀───────────────── │   monitor.py  │
          └──────────────┘   安全停/继续/新TPG   └──────┬────────┘
                 ▲                                      │ FaultReport
                 │                                      ▼
          ┌──────┴───────┐                      ┌───────────────┐
          │ ⑤ 拼接器     │                      │ ② 状态估计器  │
          │  splice      │                      │  estimator.py │
          └──────▲───────┘                      └──────┬────────┘
                 │ 新任务序列                           │ 测得状态 S_m + 动态位置
          ┌──────┴───────┐                      ┌──────▼────────┐
          │ ④ 重编译     │ ◀──────────────────── │ ③ 恢复规划器  │
          │ compiler     │   新时间表            │  recovery.py  │
          │ (当前 q 起)  │                      │ (复用 pipeline)│
          └──────────────┘                      └───────────────┘
```

### ① 监视器 `simbridge/monitor.py`
- 输入：控制器已有的事件流（`node_started/completed`、`abort` 的各类原因：`tracking_failure`、`collision_failure`、抓取对准超差、放置超差、支撑载荷缺失、所有权不匹配）+ 每 0.1 s 一次的积木位姿/夹爪状态/支撑力测量。
- 输出：`FaultReport{kind, arm, part, slot, node_id, t_detect, measurements}`。`kind` 只取第 3 节的通用类别，不含场景信息。
- 控制器改动：`abort` 不再直接终止，而是发 `fault` 事件并执行**安全停**协议（§6）。

### ② 状态估计器 `simbridge/estimator.py`
把测量换算成规划层能直接用的东西，这是泛化的关键：
- **符号事实**：对每块积木，按与槽位/位置参考位姿的误差判定
  `installed(b, s)`（在槽位内且已吸合）／`at(b, loc)`（在已知位置上）／`at(b, dyn_k)`（在任意新位置：自动创建动态位置 `dyn_k`，kind=stock，pos=测得位姿，并注册到 Frames）／`held(arm, b)`（夹爪所有权 + 距离）／`supporting(arm, s)`（支撑力 ≥ 阈值）／`free(arm)`／`arm_at(arm, cur_arm)`（当前 TCP 作为动态位置）。
- **稳定性校验**：用已有的 `hooks.invariant` 检查 S_m；若违反（例如悬臂梁无支撑无配重），标记为"结构已不稳"，恢复目标里自动加入先恢复支撑的约束（§4.3）。
- **可处理性判断**：积木侧翻/叠放/掉出工作台 → 报"不可自动恢复"，终止并记录；其余进入恢复。

### ③ 恢复规划器 `simbridge/recovery.py`
构造一个新的 Problem' 并调用**同一个** `pipeline.run(problem', backend=CoppeliaBackend)`：
- `initial = S_m`，`goal` 不变，`objects` 加上动态位置。
- **能力更新**（由故障类别决定，§3 表）：暂时性 → 对应能力记 UNKNOWN 并配重试额度；持续性 → 记 INVALID。
- **排除约束**：`(S_m, 失败动作, 路径版本)` 加入 cuts，和原项目一样精确绑定，不扩大。
- **保护事实**：`supporting(·)`、`held(·)` 在持续支撑约束下不可被随意删除（`search(protected=...)` 已支持）。
- **重试策略**：同一 (臂, 技能) 的暂时性故障最多重试 N 次（默认 2），超过升级为持续性。等价于原项目的 `RetryPolicy`，但按能力表而不是按场景写。
- 输出新的时间表 + 任务图，带恢复时间预算（默认 60 s 墙钟，超时退化为"只重试当前动作"）。

### ④ 重编译
现有 `MotionCompiler`，起点改为**两臂当前关节、当前手持、当前已放置**（`reset(from_measured=...)`）。路径缓存按上下文键自然失效，不用特殊处理。

### ⑤ 拼接器 `splice`
- 未受影响臂：允许继续执行到**下一个跨臂依赖点**（Type-2 边）之前，然后等待；若它正持物/支撑，保持。
- 受影响臂：安全停后作为新 TPG 的起点。
- 新 TPG 用新任务序列重建（不是修补旧图），`reference_order` 续接旧的，旧图已完成节点冻结。
- 时间线记录：`t_fault`、`t_detect`、`t_replan_done`、`t_resume`、`t_finish`，用于指标。

## 3. 通用故障类别（恢复族 R1–R7）

每类都定义：**注入方式**（仿真里怎么造出来）、**检测信号**、**事实变化**（估计器输出）、**能力/约束更新**（恢复规划器输入）。恢复算法本身不区分这些类别，只消费后三列。

| 族 | 故障 | 注入 | 检测 | 事实变化 | 能力/约束更新 |
|---|---|---|---|---|---|
| **R1 抓取失败/滑落** | 抓空，或搬运途中掉落 | 抓取时不建立约束；或途中解除约束 + 随机小冲量 | 夹爪所有权 ≠ 积木距离 | `held` 消失，`free(arm)`，`at(b, dyn_k)` | 暂时：`grasp(arm,b)` UNKNOWN + 重试额度；持续：INVALID |
| **R2 臂/技能持续失效** | 某臂某技能永久不可用（电机、夹爪、插装） | 禁用该臂关节使能 / 夹爪传感器；或让插装动作连续超差 | 跟踪超差 / 连续重试失败 | 无（世界未变） | `reach(arm, *)` 或具体技能能力 → INVALID；臂若完全失效则其 `free` 保留但所有动作 INVALID |
| **R3 放置/插装偏差** | 放下后积木偏移或倾斜超过容差 | 释放瞬间施加偏置冲量 / 释放位置人为偏移 | 放置超差事件 + 位姿测量 | `installed` 不成立 → `at(b, dyn_k)`；槽位 `empty` | 本次 `insert` 加 cut；若是底层积木，上层动作自然被前提阻断 |
| **R4 支撑丢失/结构扰动** | 支撑臂被中断；或外力撞击已装结构 | 支撑力归零 / 对已装积木施加冲量使其脱离 | 支撑力 < 阈值 / 已装积木位姿漂移 | `supporting` 消失；受影响积木变 `at(b, dyn_k)`，其上层连带 | 稳定性不变量驱动：恢复方案必须先恢复支撑或先拆再装 |
| **R5 交接失败** | 接收臂抓空，或交出臂未松开 | 接收抓取不建约束 / 交出释放被跳过 | 所有权不匹配事件 | 积木仍 `held(giver)` 或掉落 `at(b, dyn_k)` | 暂时：`handover` 重试；持续：该交接点对该臂 INVALID → 改走中转位 |
| **R6 路径被挡** | 自由运动途中碰到不该在那里的物体 | 把一块闲置积木移到某条路径上 | 实际碰撞事件 / 预检碰撞 | 挡路积木 `at(b_x, dyn_k)` | `(S_m, 动作, 路径版本)` 加 cut；重编译自然绕开或换臂 |
| **R7 速度退化** | 某臂被限速（如安全降速） | 控制器降低该臂速度上限 | 跟踪延迟 | 无 | 该臂 `speed` 下调 → cost 变化 → 可能改变分配 |

R1–R6 每族都有**暂时性**和**持续性**两种参数化：暂时性注入一次后消失，持续性注入后一直存在。R7 只有持续性。

## 4. 泛化性的证据设计

### 4.1 场景矩阵
恢复场景 = **任务族 × 故障族 × 时机 × 持续性**，全部由生成器随机产生，不手写：

| 维度 | 取值 |
|---|---|
| 任务族 | F1 平铺、F2 跨区交接、F3 塔墙、F4 臂托悬臂、F5 支撑台悬臂（v1.3 生成器） |
| 故障族 | R1–R7 |
| 时机 | 随机选一个动作的某个原语（接近 / 下降 / 抓取 / 抬起 / 转移 / 释放）或随机时刻 |
| 持续性 | 暂时 / 持续 |
| 故障对象 | 随机臂、随机积木（受族约束：R4 只在有支撑的任务里，R5 只在有交接的任务里） |

不是每个格子都有意义（例如 F1 没有支撑），生成器按"该族里是否存在相应结构"自动跳过并记录。

### 4.2 两层验证（和 v1.3 一样的套路）
- **规划层（广度）**：不开仿真器，把故障直接注入符号状态（估计器的输出可以离线构造），跑恢复规划器。目标 **500 个**恢复场景：每个任务族 100 个，故障族和时机随机。指标：恢复求解率、恢复后工时相对原工时的增量、重搜扩展状态数、是否触发换臂/中转/拆装。
- **仿真层（深度）**：真实注入、真实检测、真实恢复执行。目标 **40 个**：7 个故障族各 5–6 个，覆盖 5 个任务族，暂时/持续各半。指标：检测延迟、恢复规划时间、恢复执行成功率、从故障到完成的总时间、未受影响臂的空闲时间。

### 4.3 三条基线
每个仿真场景都和下面对比，证明"在线恢复"不是"重来一遍"：
1. **只重试**：原动作重试到额度用完，不重规划。
2. **全部停下重来**：两臂都停，从测得状态重新规划（不保留另一臂的进度）。这是原项目的方式。
3. **先知**：一开始就知道故障会发生（能力表预先写好），直接规划。作为时间下界。

我们的方法应当介于 2 和 3 之间，且对 R2/R5 类明显优于 1。

### 4.4 泛化性的论证方式
- 同一份恢复代码在 5 × 7 的矩阵里跑，代码里没有任何任务名和故障名的分支（可以用 grep 证明）。
- 每个格子报告成功率和时间增量；失败逐个归因到"估计器判不可恢复"、"规划无解"、"运动编译 UNKNOWN"、"执行再次失败"四类。
- 与原项目对照：Scene1 的 180.82 s / 115.50 s 可以作为 R2 持续/暂时在 F2 类任务上的参考点，说明新框架在不手写模型的情况下达到同级别的恢复时间。

## 6. 安全停协议（两臂都适用）
1. 收到 `fault`：受影响臂立即停在当前关节；若正持物则保持夹持，若正支撑则保持支撑。
2. 未受影响臂：完成当前节点；若下一节点有指向受影响臂的 Type-2 依赖则等待，否则继续，直到遇到依赖或自己的动作序列结束。
3. 监视器拍一次完整测量，交给估计器。
4. 恢复规划期间两臂保持；规划超时则退化为"只重试当前动作一次"，再失败则终止并报告。

## 8. 已确认的决定（2026-11-15）

| # | 议题 | 决定 |
|---|---|---|
| 1 | 故障范围 | **R1–R6 必做，R7 限速可选**。"传感器误报"明确列为不考虑（感知层问题） |
| 2 | 另一只臂停不停 | **第一版全停**（两臂停、从测得状态重规划、换 TPG 重启）；"未受影响臂继续到下一个跨臂依赖点"作为后续升级项，升级后对比两者时间差 |
| 3 | 持续性失效粒度 | **技能级失效为 R2 主形态，整臂失效为子类**。整臂失效边界规则：空手 → 正常恢复；持物 → 该积木标记不可用，有同类型备用块则换块，否则判不可恢复；正在支撑 → 支撑视为持续有效，另一臂完成装配，最后不要求其松开 |
| 4 | 掉落积木范围 | **只处理平放（任意偏航）**；叠在别的积木上、侧翻、掉出台面一律判不可自动恢复，单独计数。R1 注入在低处（抬起后 5 cm 内或转移前半程）触发，让落地姿态大概率平放；真侧翻如实记录，不混进成功率 |
| 5 | 验证规模 | **规划层 500 + 仿真层 20**（6 族各 3–4 个，覆盖 5 个任务族，只从 v1.3 已端到端通过的任务里抽）；基线先做"全停重来"，"先知"离线计算；补到 40 个和"只重试"基线为第二档 |
| 6 | 排期 | **明早看完 v1.3 过夜报告再发 R-M1 交接单**，避免与 Codex 今晚改 `gen/` 撞车。R-M1 纯规划层，可与 M4/M5 补跑交替进行；R-M2 以后等 M4 通过再开 |

受决定影响的章节修订：§3 中 R7 标为可选；§6 安全停协议第 2 条在第一版中改为"未受影响臂完成当前节点后停下"；§4.2 仿真层数量改为 20；§7 里程碑 R-M4 改为"20 个仿真场景 + 全停基线"。
