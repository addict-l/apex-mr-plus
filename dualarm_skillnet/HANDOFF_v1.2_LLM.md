## 2. 第一部分：配置小模型环境

### 2.1 检查硬件
1. 用 `nvidia-smi` 查看显卡型号和显存；没有 NVIDIA 显卡或命令不存在时如实记录。
2. 查看系统内存，以及 C 盘和 D 盘的剩余空间（D 盘需要至少 15 GB）。
3. 选择运行方式：
   - 显存 ≥ 8 GB：用 GPU 运行 4 位量化的 7B 模型（Ollama 默认的量化版本即可）。
   - 显存不足 8 GB 或没有 NVIDIA 显卡：仍然使用 7B 模型，允许部分或全部在 CPU 上运行，在记录里写明，并实测推理速度。

### 2.2 安装 Ollama 并下载模型
1. 安装 Ollama（安装位置保持默认，即 C 盘），确认 `ollama --version` 能输出版本号，并确认本机服务在 `127.0.0.1:11434` 运行。安装包的下载与安装按以下规则：
   - **只用单连接下载**，不要并行或分段下载。下载目录为 `out/ollama_installer/`。
   - 已有的 `out/ollama_installer/prefix.bin`（约 104 MiB）是之前从官方地址单连接下载的前缀，**从它的末尾断点续传**，不要重新下载。
   - 遇到超时、连接中断、TLS 握手失败等临时网络错误时，**允许自动重试，最多 5 次**，每次间隔依次为 10、30、60、120、300 秒，每次都从当前已下载的长度续传。全部用完仍失败，才停下报告。
   - 下载完成后，必须核对：文件总长度等于服务器声明的长度；SHA256 等于官方发布的值（与 winget 元数据一致）。任一项不符，删除该文件并停下报告，**不得运行**。
   - 安装前确认 C 盘剩余空间不少于 8 GB；安装后再记录一次 C 盘剩余空间。
   - 用核对通过的安装包静默安装到默认位置；如弹出管理员权限或确认框，停下等用户处理。
2. **下载模型之前**，先把模型存放位置设为 `D:\ollama\models` 并重启服务；下载完成后确认模型文件确实在这个目录里，并记录占用的空间。
3. 模型选择：**通义千问（Qwen）系列的 7B 指令模型**，优先在 Ollama 官方模型库中选当前可用的最新版本（例如 `qwen2.5:7b-instruct` 这一类名称，以实际存在的为准）。官方库下载失败或速度异常时，按第 1 节改从魔搭社区拉取同一系列、同一规模的官方 GGUF 版本（4 位量化）。记录实际来源、确切的模型名称和摘要值（digest）。
4. 不要下载 7B 以外规模的模型。

### 2.3 冒烟测试
用标准库 `urllib` 写一个脚本 `tools/check_model.py`，调用本机接口完成两项测试：
1. 让模型用中文回答一句简单问题，确认能正常输出。
2. 用本项目的 `build_prompt(problem, mode="with_capabilities")` 生成 `tasks/s1_reach_handover.toml` 的提示词，要求模型按 JSON 格式输出，确认 `parse_model_output` 能解析。

每项都记录耗时。

### 2.4 写环境记录
新建 `ENV_SETUP.md`，写明：显卡型号与显存、系统内存、C 盘和 D 盘剩余空间、模型存放目录及占用空间、Ollama 版本、模型来源（官方库或魔搭社区）、模型名称与摘要值、运行方式（GPU / CPU / 混合）、冒烟测试结果和耗时、遇到的问题。**再写一节“如何在另一台电脑上复现”**，按步骤列出安装和下载命令。

## 3. 第二部分：接入规划链路

### 3.1 模型调用
在 `skillnet/decompose/` 下新增 `ollama.py`，实现 `OllamaDecomposer`，满足 `SPEC.md` 第 9.1 节的 `Decomposer` 接口：
- 只用标准库 `urllib` 调用 `http://127.0.0.1:11434/api/generate`（或 `/api/chat`），非流式。
- 可配置：服务地址、模型名、超时（默认 120 秒）、`temperature`（默认 0）、`seed`（默认固定值），保证同一输入多次运行结果一致。
- 使用 Ollama 的 JSON 输出约束（`format` 参数）。
- 解析失败时，把错误原因作为反馈再请求一次，最多重试 2 次；仍然失败则返回带中文原因的异常，由 pipeline 记录并退回“不使用模型”。
- 服务未启动或连接失败时，给出清楚的中文提示：“未检测到本机 Ollama 服务，请先启动 Ollama”，然后退回“不使用模型”，不能让程序崩溃。
- 记录每次调用的耗时、模型名、提示词长度和原始输出，写入结果文件。

### 3.2 任务指令
给 `tasks/` 下每个任务文件增加顶层字段 `instruction`：一句自然、口语化的中文任务描述，例如“把红色积木放到底板左边那个位置”。要求：
- 只描述要做成什么，**不能透露解法**：不写谁够得着哪里，不写要交接、要托住或要搭台。
- `*_with_proposal.toml` 与对应的原任务使用相同的指令。

提示词生成时优先使用 `instruction`，没有时退回 `description`。

### 3.3 模型给出的目标
模型输出中的 `goal` **不替代**任务文件的目标（验收依据不变），但要在报告中对比：模型目标是否覆盖了任务文件的全部显式目标、是否包含多余或错误的条件。

### 3.4 命令行
- `run TASK --model NAME [--mode minimal|with_capabilities] [--host URL]`：用真实模型生成方案，代替任务文件里的 `[proposal]`。
- `experiment [--model NAME] [--out DIR] [--tasks ...]`：运行第 4 节的对比实验。

## 4. 第三部分：对比实验

### 4.1 实验设置
对以下 9 个任务（不含两个 `*_with_proposal.toml`）分别运行三种设置：

| 设置 | 说明 |
|---|---|
| `none` | 不使用模型，直接搜索 |
| `minimal` | 模型只拿到任务、场景和技能清单 |
| `with_capabilities` | 模型额外拿到每只臂的能力摘要 |

### 4.2 记录的指标
每个任务、每种设置记录一行：
- 模型输出是否为合法 JSON、重试次数；
- 模型步骤数；校验补全中保留、补出、删除、多余的步数；
- 删除原因中能力不通过的次数；
- 模型目标与任务目标的对比结果（第 3.3 节）；
- 补全后是否达成目标；
- 最终结论、完成时间；
- 搜索扩展状态数、搜索用时；
- 模型推理耗时。

### 4.3 输出
写到 `results/llm_v1_2/`：`experiment.csv`（全部原始数据）、`summary.md`（中文汇总表和简短结论）、每次调用的提示词和原始输出（便于复查）。

## 5. 验收标准（全部满足才算完成）

1. `ENV_SETUP.md` 完整；`python -X utf8 tools/check_model.py` 两项冒烟测试都通过。
2. 原有 173 项测试全部通过。新增测试**不依赖真实模型**：用标准库 `http.server` 在测试里启动一个本地模拟服务，覆盖正常输出、非法 JSON 后重试成功、多次失败后退回、服务未启动四种情况。
3. 真实模型的集成测试默认跳过，只有设置环境变量 `SKILLNET_LIVE_MODEL=1` 时才运行；在本机设置该变量后运行，必须通过。
4. `experiment` 在本机用真实模型跑完 9 个任务 × 3 种设置，`summary.md` 生成。
5. **使用模型不得改变最终结果**：每个任务三种设置下的最终结论都是 `solved`，完成时间与 `none` 一致（误差不超过 1e-6）。如果不一致，说明模型方案影响了最优性，必须查明原因并修复。
6. 所有任务文件都有 `instruction`，并且不透露解法。
7. README 的“v1.2 修订”一节写明：环境配置结果、接入方式、实验结果摘要、发现的问题。
