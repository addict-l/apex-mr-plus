**APEX_MR_Plus 正常模式：分工、参考运动、TPG 与动力学执行**

本目录实现正常能力条件下的双 UR5 装配基线，采用 [APEX-MR 原文](https://arxiv.org/html/2503.15836v3) 的分层思路：给定装配顺序，选择执行臂、抓取和支撑模式，生成顺序参考动作与关节路径，再构造多模态时间计划图，由中央调度器根据实际完成事件协调执行。

2026-10-28 的完整“规划—调度—装配”已通过实际动力学验收：7 块积木、53 条参考动作、165 个 TPG 节点全部完成，176 条边的前驱完成条件全部满足；7 次抓取和 7 次扣接均有实际事件记录，全部机械臂关节、工具和连接传感器均启用动力学。实际耗时 143.80 s，最大位置误差 1.60 mm，最大姿态误差 0.00154 rad，支撑反力峰值 13.84 N。加载 8 N 时桥面连接力矩峰值 0.539 N·m；全程所有连接力矩峰值不超过 0.969 N·m，低于 1.2 N·m 限值。15 项测试通过。

同一时间缩放下，串行参考为 180.92 s，TPG 名义预测为 130.73 s；二者是计划时间，143.80 s 才是本次实际完成事件的执行耗时。结果对应单次完整验收，不声称多次试验成功率或全局最优。原始证据见 `../results/normal/summary.json`、`execution.json`、`execution_validation.json`；此前失败诊断保存在 `diagnostics/`。本次关闭录像，已保存实际装配完成画面和支撑安装画面，未生成本次 MP4。

**正常任务与输入。** 主场景为 `../scenes/10_Normal_Assembly.ttt`。七个可动部件依次为 `L1、R1、L2、R2、L3、beam、cap`：左塔三层、右塔两层、悬臂桥面和连接砖。装配次序及前提关系作为输入给定；本版本不搜索城堡设计，也不自动生成装配顺序。场景使用放大的模块化积木，不采用真实 LEGO 尺寸。

`scene.py` 保存几何、质量、惯量、源位置、目标位置、抓取候选、连接力矩限值和插装载荷。`NormalAssembly` 自定义数据包含 `parts、arms、blocks、initial、goal、sizes、obstacles、physics`；加载场景后调用 `resolve(sim)` 重新解析实时对象句柄，不依赖旧文件中的数值句柄。规划障碍至少包含城堡底板与左右料盘，桌面单独检查。

**从输入到执行的步骤。**

1. `compile.py` 用实际 `simIK` 求解候选源位、抓取位、抬升位、目标接近位和放置位，并检查场景几何，产生 `candidate_qualification.json`。候选中包含执行臂、抓取方式、负载相对 TCP 位姿，以及可用的支撑臂和支撑接触位姿。端点可达不等于连接路径已可行。
2. `allocation.py` 的 `solve_allocation(problem)` 调用 `scipy.optimize.milp / HiGHS`。每个部件恰选一个“执行臂—抓取—支撑方式”模式；执行臂不能同时充当支撑臂；无效候选不能被选中。目标是估计关节运动代价、支撑代价与最大臂负载的加权和，并非异步执行完工时间的全局最优值。结果保存每个模式变量、目标值、MIP gap 和支撑判据。
3. 编译器把选中模式展开为两臂的顺序任务，包含 `Transit、Pick、Place、Support、Release support`。每段参考关节路径由 `simOMPL` 的 **RRTConnect** 求解，保存真实关节样本及持物、已装结构和接触豁免条件。若选中模式的路径求解失败，就禁用相应候选后重新求解分工，不以未验证的直线动画补齐失败路径。
4. `tpg.py` 的 `build_tpg(tasks, conflict_oracle, ...)` 将移动路径分成位姿片段，将接触技能保留为技能节点。同臂 Type-1 边维持既定顺序；跨臂 Type-2 边记录任务前提和几何冲突。冲突边按可行串行参考的先后方向加入，并检查图无环；构图本身不承诺最短 makespan。
5. `geometry.py` 的 `SampledConflictOracle` 检查两臂路径片段的所有相对采样状态，同时考虑各自持物。Type-2 构图使用 `fast_interarm.py/.lua` 的原生物理碰撞代理与明确工具几何，不用高密度纯视觉外壳；这个快速采样器只检查双臂及对方持物的交叉碰撞，不承担环境、自碰或自由积木检查。其保守包围盒宽相位对不相交的运动范围提前排除，重叠情况仍按 `0.07 rad` 相对相位网格检查；包围盒膨胀显式依赖本 UR5、固定工具和本场景积木的 `2 m` 祖先关节半径上界假设。RRT 路径使用完整环境检查，`verify_rollout` 再用完整 `MotionPlanner` 检查名义同时运动、持物、已放结构和静止等待端点。`program.py` 在不改变已规划折线路径的前提下，对各段使用五次静止到静止时间缩放，名义关节速度/加速度上限分别为 `0.60 rad/s`、`1.20 rad/s²`。
6. `runtime.py` 把 `controller.lua` 嵌入 `11_Normal_APEX_MR_Planned.ttt`。中央调度器仅在所有前驱实际完成、机械臂资源可用时下发下一节点。运行中通过 `sim.setJointTargetPosition` 驱动动态关节，并根据实际关节跟踪和端点稳定时间确认完成；不会按名义时间表直接把节点判为完成。名义时间用于参考与可视化，真实开始/结束时间来自仿真日志。

**支撑如何选择。** 输入采用连接处的准静态力矩筛选：

\[
M_{\mathrm{required}}=(m g+F_{\mathrm{insert}})\,l,
\qquad
M_{\mathrm{required}}>M_{\mathrm{limit}}
\Longrightarrow \text{禁用无支撑模式}.
\]

`mass` 的单位为 kg，`insertion_force` 为 N，`lever_arm` 为 m，`connection_moment_limit` 为 N·m。力矩未超限时允许选择无支撑模式；超限时必须存在另一只机械臂可执行的支撑候选。这个判据描述给定加载点的保守近似，不能独自证明接触力锥、全部抓取承载或动态装配过程都可行。

支撑任务有显式的建立/解除依赖。动态支撑鞋通过独立 PadFT 与手掌相连；非支撑阶段关闭鞋的碰撞响应。控制器把 PadFT 力转换到世界 Z 方向，去除空载基线，记录支撑反力幅值；插装阶段检查实际支撑证据。插装载荷通过对已有结构施加指定外力及其等效力矩进行建模。它是可核查的负载试验，不代表已经实现真实夹爪的接触力闭环控制。

支撑候选除逆解和避碰外，还必须通过实际接触面的几何资格检查：支撑鞋与梁底的投影接触区域沿 X、Y 两方向均有至少 `2 mm` 的正重叠，不能把“不碰撞”或边缘擦过当成有效支撑。候选包含 `y=0.160 m` 的接触位置，并使用鞋的真实尺寸、方向及实现的 TCP 姿态重新核对投影接触；具体选中位置与接触证据保存在候选资格文件。

支撑技能采用分段接近：先在梁外下降，再沿梁下 `3 mm` 净空水平进入，最后竖直上托；退出时按反向阶段先下降解除接触、再水平移出、最后在外侧抬升。各段仍由真实 RRT-Connect 生成参考关节路径，分段路径与净空记录在技能元数据中。接触建立和撤离的名义速度、加速度限值收紧为 `0.025 rad/s`、`0.12 rad/s²`，不沿用普通搬运的较高上限。

执行器必须测得超过 `0.15 N` 的去基线支撑反力，并持续满足端点稳定时间要求，才发布 `support_ready` 完成事件、放行连接砖的 `8 N` 插装加载。对结构沉降的支撑高度参考修正限于 `2 mm`，补偿在虚拟 IK 环境计算，真实机械臂继续由动态关节伺服跟踪修正后的参考。SnapFT 的连接力矩超过 `1.2 N·m` 且连续达到 10 帧时报告失败。几何资格、反力就绪和连接矩监测各自提供不同证据，完整装配是否通过仍由本次实际执行验收决定。

**动力学模型。** 仿真采用 Bullet 刚体求解，重力为 `[0, 0, -9.81] m/s²`，场景步长 `0.02 s`、动力学子步长 `0.002 s`、求解迭代数 150。对桌面、底板和积木设置名义摩擦系数 0.8、零恢复系数；Pad 和原生 UR5 沿用各自材料参数，不能把 0.8 解释为所有接触对象的统一材料系数。模型遵循机械臂动力学关系：

\[
M(q)\ddot q+C(q,\dot q)\dot q+g(q)
=\tau+J(q)^\mathsf{T}F_{\mathrm{ext}}.
\]

其中 `q` 为关节角，`M` 为惯性矩阵，`C q̇` 为科氏/离心项，`g` 为重力项，`τ` 为关节驱动力矩，`JᵀF_ext` 为外部接触载荷映射到关节的广义力。Bullet 根据原生 UR5 的刚体质量、惯量、重力、约束和接触求解运动。前三个关节的位置伺服驱动力矩上限为 `200 N·m`，后三个为 `50 N·m`；规划输出关节路径，再用上述 quintic 时间缩放限速、限加速度。本实现不包含机器人参数辨识、实机参数标定或最优动力学轨迹规划，名义运动界也不能替代实际关节速度和跟踪误差日志。

- UR5 使用安装包原生模型的名义连杆质量和惯量，根基座固定，六个关节使用动态位置伺服。新增工具与部件使用明确质量和长方体质心惯量；每次运行导出 `rigid_bodies.json`。
- 工具力链为“末端动态连杆 → ToolFT → 动态手掌”。原生模型的 `connection` 本身也是力传感器，因此新增 ToolFT 直接挂到真实动态连杆，避免两个力传感器连续而无法启用。
- 支撑链为“动态手掌 → PadFT → 动态支撑鞋”。手指和积木凸点不参与动力学接触，实际积木接触体为长方体；几何规划仍使用明确的 Palm/Finger/SupportShoe 工具代理，不能把动力学响应关闭误解为规划中忽略工具几何。
- 抓取采用“动态手掌 → GraspFT → 动态积木”的理想刚性约束，保持实际抓取时的世界位姿。释放后部件仍为动态刚体。
- 扣接采用部件实际到达位姿处建立的 SnapFT 刚性连接，保持实测位姿，不把部件传送到目标。控制器监测连接力矩并在超限时报告失败。该模型没有摩擦夹持、LEGO 卡扣弹性、插拔变形或真实连接破坏过程。

静止验证记录在 `../results/normal/dynamics_fix.json`：50 帧内 12 个关节、ToolFT、PadFT、支撑鞋及七个部件均实际启用动力学，力数据有效；基座世界漂移为 0，双臂 TCP 漂移约 33 μm，最大关节目标误差约 `5.47e-5 rad`，源部件最大沉降 1.5 mm，初始静态穿透为 0。这些数据验证静止保持和源件稳定，不证明负载搬运或完整装配已经成功。

**运行入口。** 双击项目根目录的 `Run_Normal_Mode.cmd`，默认尝试复用同一场景的 ILP/参考路径及 TPG，随后仍会重新检查名义几何并进行真实动力学执行。这是日常复跑入口；它不会把缓存中的时间表当作已执行结果。双击 `Replan_Normal_Mode.cmd` 会从候选资格、ILP、RRT-Connect 到 TPG 重新计算，再执行动力学，耗时更长。

这两个入口都把过程输出保留在终端并在结束后暂停，便于查看失败阶段。正常源场景 `../scenes/10_Normal_Assembly.ttt` 必须存在。两入口均接受附加参数，例如：

```powershell
.\Run_Normal_Mode.cmd --no-video
.\Replan_Normal_Mode.cmd --plan-only
```

等价命令行如下；它们读取 `10_Normal_Assembly.ttt`，不会自动把尚未验收的计划覆盖成顶层主场景：

```powershell
cd D:\APEX_MR_Plus
python -m normal.pipeline --reuse-reference --reuse-tpg
python -m normal.pipeline --replan
```

只检查完整规划输出、暂不执行动力学：

```powershell
python -m normal.pipeline --replan --plan-only
```

`--no-video` 关闭录像。复用入口缺少某个缓存时，流水线会计算缺失产物；已有缓存会检查场景与参考路径签名。改变几何、HOME、源位置、质量、能力、抓取工具或碰撞代理后，应重新生成相应源场景并使用 `--replan`。签名覆盖范围以 `pipeline.py` 为准，不能检测所有工具或静态地物编辑。`--plan-only` 只生成和验证规划，不产生实际装配成功证据。`Open_APEX_MR_Plus.cmd` 只打开当前顶层主场景，功能与两个正常执行入口不同。

**输出与接口。** 所有运行数据位于 `../results/normal/`；输出只在对应阶段完成后才会出现。

- `problem.json、rigid_bodies.json`：物理任务、名义质量和惯量。
- `candidate_qualification.json、allocation_problem.json、allocation.json`：几何资格、MILP 输入与分配结果；`planning_failures.json` 记录运动失败导致的模式禁用。
- `reference_tasks.json / tasks.json`：参考技能和真实关节路径；`alloc_and_reference.json、motion_stats.json` 保存编译结果和运动求解证据。
- `sequential_task_graph.json`：按 A/B 分组的顺序任务图，包含给定装配顺序及所选分配。`tpg.json` 保存位姿/技能节点、Type-1/Type-2 边、碰撞采样证据、名义调度和时间参数化。
- `geometry_pair_checks.jsonl、geometry_statistics.json、nominal_geometry_validation.json`：跨臂采样检查与名义调度/等待检查。
- `normal_pipeline_tpg.png / .svg`：与论文形式相近的三行图，显示串行任务、RRT-Connect 参考运动和多模态 TPG 异步计划。`normal_execution_timeline.png / .svg` 对照名义调度与实际执行；没有执行日志时不合成假执行数据。中断日志中尚无结束时刻的任务只截断到日志停止时刻，并以红色斜线、叉号和“执行中断”标明，不能解释为正常完成。
- `execution.json`：实际节点事件、任务时间、关节位置/速度/力矩、部件位姿、工具与支撑力、连接状态、误差和失败原因。`summary.json` 的 `success` 是本次端到端验收入口，须与同一次运行的执行日志核对。
- `execution_validation.json`：对该次实际日志独立核查节点依赖、单臂占用、支撑反力就绪、8 N 加载、连接矩与目标误差等条件；它不是名义 TPG 的几何预测。`normal_dynamics_validation.png / .svg` 从该日志绘制跟踪、速度、支撑与插装载荷等动力学验收曲线。
- `delivery.json`：记录通过验收后的主场景路径、文件 SHA-256 和动作数；当前主场景已更新。打开后点击 ▶ 可从初始料盘状态执行嵌入的 TPG，无需在播放时运行外部 Python 规划器。
- `normal_execution.mp4`：实际仿真相机录像；可靠的耗时数据应读取日志中的仿真时间，而非根据视频帧数推算。`initial_dynamic_scene.png、completed_dynamic_scene.png` 或 `failed_dynamic_scene.png` 保存对应实测画面。
- `pipeline_manifest.json`：场景签名、流水线阶段及理想化模型边界。`../scenes/11_Normal_APEX_MR_Planned.ttt` 包含已生成计划和中央调度脚本。

**与 APEX-MR 的关系。** 本实现沿用 ILP 分工、串行可行参考、RRT-Connect、多模态 TPG 和实际完成反馈调度这条主线；没有复刻原论文的全部 ILP 公式、装配序列生成、EOAT、力控制技能或可选 shortcut 优化。实际碰撞验证采用有限采样，不能据此宣称连续时间、任意延迟下的完整碰撞保证；TPG 无环也不意味着装配动力学或接触过程必然成功。问题①的已知故障演示从正常模式的已规划场景派生，复用本目录的运动规划、TPG 和动力学调度。运行方式见 [恢复演示说明](../recovery/README.md)。
